Shedflare Onboarding Guide A deep dive into the Chat and Drive apps, Effect patterns, and authoring conventions

This guide is written for developers who are new to the Shedflare codebase but already comfortable with TypeScript. It assumes you understand what Effect is at a conceptual level (it's a library for typed, composable effects) but don't yet know the syntax or how we use it here. Every section includes real code from the repo, anti-patterns to avoid, and plain-TypeScript comparisons where they help.

Overview

Shedflare is a self-hosted suite of personal productivity tools deployed on Cloudflare. It is not a SaaS — there is one user (the deployer), no sign-up flow, and no per-user isolation. Auth exists solely to protect the deployment from public access.

The suite contains seven apps, but this guide focuses on the two most architecturally interesting:

App What It Does Storage Real-Time
Chat AI chat with web search, file attachments, tracing Durable Object SQLite WebSocket sync
Drive File storage with tags, public sharing D1 + R2 No (request/response)

These two apps represent the two main architectural patterns in the repo:

  • Chat pattern: Durable Object with WebSocket-based sync protocol, event sourcing, and optimistic updates
  • Drive pattern: Standard Worker with D1/R2, Effect HttpApi for typed REST endpoints

The Sync Protocol

The sync protocol is defined in packages/sync-protocol/ and extended by the chat app. It's a typed WebSocket protocol with message envelopes.

Client → Server Messages

Type Purpose
hello Initial handshake — sends clientId, protocolVersion, lastServerSeq, unackedOpIds
command A sync command — opId, commandType, payload
resume Resume after reconnect — sends lastServerSeq to catch up

Server → Client Messages

Type Purpose
hello_ack Handshake response — protocolVersion, serverTime, lastServerSeq
ack Command accepted — opId, serverSeq, acceptedAt
reject Command rejected — opId, reason, code, retriable
event Data change — serverSeq, eventId, eventType, payload
sync_reset Full snapshot replacement — when protocol version changes or cursor is stale

The protocol uses sequence numbers (serverSeq) for ordering and operation IDs (opId) for deduplication. Every command gets exactly one ack (or reject), and every event is sequenced so clients can resume from where they left off.

The Durable Object

apps/chat/src/server/sync-engine.ts — SyncEngineDurableObject extends SyncEngineDO<AppEnv> from the shared sync-protocol package. 

export class SyncEngineDurableObject extends SyncEngineDO<AppEnv> {
  private readonly db: DrizzleSqliteDODatabase<typeof dbSchema>;
  private readonly chatAccess: DataAccess;
  private readonly eventStore: EventStore;
  private readonly assistantTurnControllers = new Map<string, AbortController>();
  private readonly chatHandlers = new Map<SyncCommandType, ChatHandlerFn>();

  constructor(ctx: DurableObjectState, env: AppEnv) {
    super(ctx, env);
    this.db = drizzle(ctx.storage, { schema: dbSchema, logger: false });
    this.chatAccess = new DataAccess(this.access, this.db);
    this.eventStore = new EventStore(this.chatAccess);
    this.registerChatHandlers();

    // Run DDL on cold start — blockConcurrencyWhile ensures this completes
    // before any requests are processed
    void ctx.blockConcurrencyWhile(async () => {
      initializeStorage(
        (query, ...params) => ctx.storage.sql.exec(query, ...params),
        // ...
      );
    });
  }
}
Key Concept — blockConcurrencyWhile
Durable Objects process requests one at a time (single-threaded). blockConcurrencyWhile ensures that the initialization (DDL, migrations) completes before the DO accepts its first request. Without this, a request could arrive before the schema is ready.

Command Processing Flow

private async processChatCommand<T extends SyncCommandType>(
  opId: string,
  commandType: T,
  payload: SyncCommandPayloadMap[T],
  doBroadcast: boolean,
): Promise<SyncCommandResult> {
  // 1. Dedup check — if we already processed this opId, return the cached ack
  const existing = this.access.getCommandAck(opId);
  if (existing) return { ack: existing, events: [] };

  // 2. Look up the handler for this command type
  const handler = this.chatHandlers.get(commandType);

  // 3. Validate the payload against the Effect Schema
  const validatedPayload = decodeCommand(commandType, payload);

  // 4. Execute in a transaction
  const result = this.db.transaction(() => {
    const { events, followUp } = handler(opId, validatedPayload, handlerContext);
    // Write ack to commands table for dedup
    this.db.insert(dbSchema.commands).values({ opId, ... }).run();
    return { ack, events, followUp };
  });

  // 5. Broadcast ack + events to all connected WebSocket clients
  if (doBroadcast) {
    this.broadcast(result.ack);
    for (const event of result.events) this.broadcast(event);
  }

  // 6. Execute follow-up (e.g., assistant turn) via ctx.waitUntil
  if (result.followUp) {
    this.ctx.waitUntil(result.followUp());
  }

  return result;
}

Commands & Events

The chat app has 21 command types and 19 event types. Commands are typed payloads validated against Effect Schemas. Events are the resulting state changes broadcast to all clients.

apps/chat/src/domain/index.ts
// Command payload schemas — each command has a corresponding Effect Schema
export const CommandPayloadSchemas = {
  bootstrap_session: BootstrapSessionPayloadSchema,
  create_workspace: CreateWorkspacePayloadSchema,
  create_user_message: CreateUserMessagePayloadSchema,
  retry_message: RetryMessagePayloadSchema,
  cancel_assistant_turn: CancelAssistantTurnPayloadSchema,
  // ... 16 more
} as const;

// Type-safe command decoder
export function decodeCommand<K extends SyncCommandType>(
  commandType: K,
  input: unknown,
): SyncCommandPayloadMap[K] {
  const schema = CommandPayloadSchemas[commandType];
  return Schema.decodeUnknownSync(schema)(input);
}

The Assistant Turn

When a user sends a message, the chat app creates both a user message and a pending assistant message, then starts an LLM streaming turn. This is the most complex flow in the app.

apps/chat/src/server/assistant-turn.ts
export async function runAssistantTurn(
  payload: AssistantTurnPayload,
  ctx: AssistantTurnContext,
) {
  const abortController = new AbortController();
  ctx.assistantTurnControllers.set(payload.assistantMessage.id, abortController);

  // Create trace context for observability
  const traceContext = makeRootTraceContext({
    messageId: payload.assistantMessage.id,
    threadId: payload.threadId,
    modelId: payload.modelId,
  });

  // Create a trace recorder that writes spans to the DB via events
  const recorder = makeTraceRecorder({
    scope: "assistant-turn",
    onTraceRunStart: async (row) => {
      const event = await ctx.eventStore.appendServerEvent(
        null, "trace_run_upserted", { row }
      );
      ctx.broadcast(event);
    },
    // ... onTraceRunFinish, onSpanStart, onSpanFinish
  });

  // The actual LLM call, wrapped with Effect tracing
  const traceAsync = (name, kind, attrs, run) =>
    runAppEffect(
      traceEffect(name, kind, attrs, Effect.tryPromise(run)),
      { env: ctx.env, traceRecorder: recorder, traceContext: childContext },
    );

  const messages = await traceAsync(
    "assistant.thread_messages.load", "internal", {},
    () => buildModelMessages(ctx.access, payload),
  );

  const stream = await traceAsync(
    "assistant.upstream.chat", "model", { modelId: payload.modelId },
    () => chat({ model, messages, signal: abortController.signal }),
  );

  // Consume the stream and emit events
  await consumeAssistantStream(stream, { ... });
}
Why Effect for tracing?
The chat app uses Effect primarily for structured tracing, not for general control flow. Each significant operation is wrapped with traceEffect, which creates a span, executes the operation, and records the result — including errors and cancellations via Effect.onExit. This gives us detailed observability without cluttering the business logic with try/catch/finally blocks.

Turn Recovery via Alarms

If the Durable Object restarts mid-turn (e.g., due to Cloudflare eviction), the turn parameters are persisted in a pending_turns table. A DO alarm fires 30 seconds later to check for and recover interrupted turns. 

async alarm() {
  const turns = this.loadAllTurnParams();
  for (const [messageId, params] of turns) {
    const message = this.chatAccess.getMessage(messageId);
    if (!message || message.status === "completed" || message.status === "failed") {
      this.clearTurnParams(messageId); // Clean up stale entries
      continue;
    }
    // Create a new assistant message and restart the turn
    await this.recoverTurn(messageId, params);
  }
}

Effect HttpApi — Typed API Definitions

The drive app defines its API using Effect's HttpApi, HttpApiGroup, and HttpApiEndpoint. This gives you typed endpoints with schema-validated inputs and outputs.

apps/drive/src/server/definitions.ts
import { Schema } from "effect";
import { HttpApi, HttpApiEndpoint, HttpApiGroup } from "effect/unstable/httpapi";

// Define the response shape
const FileSchema = Schema.Struct({
  id: Schema.String,
  name: Schema.String,
  mimeType: Schema.String,
  size: Schema.Number,
  description: Schema.String,
  isPublic: Schema.Boolean,
  createdAt: Schema.String,
  updatedAt: Schema.String,
  tags: Schema.Array(Schema.String),
});

const FilesSuccess = Schema.Struct({
  files: Schema.Array(FileSchema),
  nextOffset: Schema.optional(Schema.Number),
});

// Define endpoints
const fileListEp = HttpApiEndpoint.get("list", "/api/files", {
  success: FilesSuccess,
});

const fileCreateEp = HttpApiEndpoint.post("create", "/api/files", {
  success: Schema.Struct({ file: FileSchema }),
});

const fileUpdateEp = HttpApiEndpoint.patch("update", "/api/files/:id", {
  params: Schema.Struct({ id: Schema.String }),
  success: Schema.Struct({ file: FileSchema }),
});

// Group endpoints and build the API
const filesGroup = HttpApiGroup.make("files").add(
  fileListEp, fileCreateEp, fileUpdateEp, fileDeleteEp,
  fileDownloadEp, filePreviewEp,
);

export const driveApi = HttpApi.make("drive").add(filesGroup, tagsGroup);

Handler Implementation

Handlers are wired up using HttpApiBuilder.group. Each handler receives the Effect context and wraps the actual logic with auth:

apps/drive/src/server/impl/files.ts
export function createFileHandlersGroup(env: FileEnv, auth: HttpApiAuth) {
  return HttpApiBuilder.group(driveApi, "files", (handlers) =>
    handlers
      .handle("list", (ctx) =>
        auth.createProtectedHandler(async (webReq) => {
          const db = drizzle(env.DB);
          const url = new URL(webReq.url);
          const search = url.searchParams.get("search")?.trim() ?? "";
          const tag = normalizeTag(url.searchParams.get("tag") ?? "");
          const limit = Math.min(Math.max(..., 1), 100);
          const offset = Math.max(..., 0);

          const rows = await db
            .select({ id: files.id, name: files.name, ... })
            .from(files)
            .leftJoin(fileTags, eq(fileTags.fileId, files.id))
            .leftJoin(tags, eq(tags.id, fileTags.tagId))
            .where(and(searchWhere, tagWhere))
            .groupBy(files.id)
            .orderBy(desc(files.createdAt))
            .limit(limit + 1)
            .offset(offset)
            .all();

          const hasMore = rows.length > limit;
          return {
            files: pageRows.map(publicFile),
            ...(hasMore ? { nextOffset: offset + limit } : {}),
          };
        })(ctx),
      )
      .handle("create", (ctx) =>
        auth.createProtectedHandler(async (webReq) => {
          const form = await webReq.formData();
          const file = form.get("file");
          // Stream file to R2
          await env.FILES.put(objectKey, file.stream(), {
            httpMetadata: { contentType: file.type },
          });
          // Insert metadata into D1
          await db.insert(files).values({ id, objectKey, name, ... });
          await setFileTags(db, id, tagNames);
          return HttpServerResponse.fromWeb(
            new Response(JSON.stringify({ file: publicFile(row) }), { status: 201 })
          );
        })(ctx),
      )
      // ... update, delete, download, preview handlers
  );
}

Router — Wiring It All Together

apps/drive/src/server/router.ts
export function createRouter(env: Env) {
  const auth = createHttpApiAuth(env);

  // Create the Effect HttpApi handler
  const wh = createHttpApiWebHandler(driveApi, [
    createFileHandlersGroup(env, auth),
    createTagsGroup(env, auth),
  ]);

  return {
    async fetch(request: Request): Promise<Response> {
      const url = new URL(request.url);

      // Auth routes (manual)
      if (pathname === "/api/auth/login") return auth.loginRedirect();
      if (pathname === "/api/auth/callback") return auth.handleCallback(request);

      // Public routes (no auth)
      if (pathname === "/api/public/files") return listPublicFiles(env, request);

      // Protected API routes → Effect HttpApi handler
      if (pathname.startsWith("/api/")) return wh.handler(request);

      // Static assets (SPA fallback)
      return env.ASSETS.fetch(request);
    },
  };
}
Pattern: Hybrid Routing
The drive app uses manual URL dispatch for auth and public routes, and delegates /api/* to the Effect HttpApi handler. This is a common pattern — you get full control over auth and public routes while letting Effect handle the typed API layer.

Storage — D1 + R2

apps/drive/src/db/schema.ts
import { index, integer, primaryKey, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const files = sqliteTable("files", {
  id: text("id").primaryKey(),
  objectKey: text("object_key").notNull().unique(),  // R2 key: files/{uuid}
  name: text("name").notNull(),
  mimeType: text("mime_type").notNull(),
  size: integer("size").notNull(),
  description: text("description"),
  isPublic: integer("is_public", { mode: "boolean" }).notNull().default(false),
  createdAt: text("created_at").notNull(),
  updatedAt: text("updated_at").notNull(),
}, (table) => [
  index("idx_files_created_at").on(table.createdAt),
  index("idx_files_is_public_created_at").on(table.isPublic, table.createdAt),
]);

export const tags = sqliteTable("tags", {
  id: text("id").primaryKey(),
  name: text("name").notNull(),
  normalizedName: text("normalized_name").notNull().unique(),
});

export const fileTags = sqliteTable("file_tags", {
  fileId: text("file_id").notNull().references(() => files.id, { onDelete: "cascade" }),
  tagId: text("tag_id").notNull().references(() => tags.id, { onDelete: "cascade" }),
}, (table) => [primaryKey({ columns: [table.fileId, table.tagId] })]);

The pattern is: R2 stores the bytes, D1 stores the metadata. File objects are keyed as files/{uuid} in R2. The D1 schema has a many-to-many relationship between files and tags via a junction table.

Effect Patterns — Schema

Schema Effect

Effect Schema is used for runtime type validation — defining the shape of data, validating incoming payloads, and deriving TypeScript types. Think of it as a more powerful, composable alternative to Zod.

Basic Schema Definition

apps/chat/src/domain/index.ts
import * as Schema from "effect/Schema";

// A simple enum — like a union of string literals
export const ReasoningLevel = Schema.Literals(["off", "low", "medium", "high"]);
export const MessageStatus = Schema.Literals([
  "queued", "pending", "streaming", "completed", "failed", "cancelled",
]);

// A struct — like a TypeScript interface
export const MessageRow = Schema.Struct({
  id: Schema.String,
  threadId: Schema.String,
  role: MessageRole,
  status: MessageStatus,
  modelId: Schema.String,
  reasoningLevel: ReasoningLevel,
  text: Schema.String,
  createdAt: Schema.String,
  errorCode: Schema.NullOr(Schema.String),    // string | null
  durationMs: Schema.NullOr(Schema.Number),    // number | null
  searchEnabled: Schema.Boolean,
  // Optional fields (may be absent from the object)
  optimistic: Schema.optional(Schema.NullOr(Schema.Boolean)),
  opId: Schema.optional(Schema.NullOr(Schema.String)),
});

// Derive the TypeScript type from the schema
export type Message = Schema.Schema.Type<typeof MessageRow>;

Decoding (Runtime Validation)

// Decode and validate — throws on invalid input
const message = Schema.decodeUnknownSync(MessageRow)(rawInput);

// This is equivalent to:
// if (typeof rawInput.id !== "string") throw ...
// if (typeof rawInput.threadId !== "string") throw ...
// ... but with much less boilerplate and better error messages

Comparison: Effect Schema vs Plain TypeScript

Plain TypeScript (type only — no runtime validation)
type Message = {
  id: string;
  threadId: string;
  role: "user" | "assistant" | "system";
  status: "pending" | "completed" | "failed";
  text: string;
  errorCode: string | null;
};

// Problem: this type disappears at runtime.
// You can't validate that incoming JSON matches it.
function handleMessage(input: unknown): Message {
  // You'd need to manually check every field...
  const obj = input as Record<string, unknown>;
  if (typeof obj.id !== "string") throw new Error("...");
  if (typeof obj.threadId !== "string") throw new Error("...");
  if (obj.role !== "user" && obj.role !== "assistant" && ...)
    throw new Error("...");
  // ... 20 more checks
  return obj as Message;
}
Effect Schema (type + runtime validation)
const MessageSchema = Schema.Struct({
  id: Schema.String,
  threadId: Schema.String,
  role: Schema.Literals(["user", "assistant", "system"]),
  status: Schema.Literals(["pending", "completed", "failed"]),
  text: Schema.String,
  errorCode: Schema.NullOr(Schema.String),
});

type Message = Schema.Schema.Type<typeof MessageSchema>;

// One-liner validation — throws with detailed error messages
const message = Schema.decodeUnknownSync(MessageSchema)(input);
Why We Use Schema
The sync protocol receives JSON payloads from the network. Without runtime validation, a malformed payload could crash the server or corrupt data. Schema gives us a single source of truth: the TypeScript type and the runtime validator are derived from the same definition.

Schema for API Definitions

Effect HttpApi uses Schema to define the shape of request params, query strings, and response bodies: 

// Params are validated automatically
const fileUpdateEp = HttpApiEndpoint.patch("update", "/api/files/:id", {
  params: Schema.Struct({ id: Schema.String }),  // :id is extracted and validated
  success: Schema.Struct({ file: FileSchema }),

Effect Patterns — Context.Services

Effect Pattern

Context Services are Effect's dependency injection system. A Context.Service defines a tag (a unique identifier) and a type (what the service provides). Other Effects can then yield* the tag to access the service.

Think of it as a typed, compile-time-checked service locator.

apps/chat/src/effect/index.ts
import { Context, Effect } from "effect";

// Define three services — each with a unique tag and a type
export const AppEnvTag = Context.Service<AppEnv>("#/effect/AppEnv");
export const TraceRecorder = Context.Service<TraceRecorderService>("#/effect/TraceRecorder");
export const TraceContext = Context.Service<TraceContextValue>("#/effect/TraceContext");

// Now any Effect can require these services:
const myEffect = Effect.gen(function* () {
  const env = yield* AppEnvTag;           // ← gets AppEnv from the context
  const recorder = yield* TraceRecorder;  // ← gets TraceRecorderService
  const context = yield* TraceContext;    // ← gets TraceContextValue

  // Use them...

Effect Patterns — Layers

Effect Pattern

A Layer is a recipe for constructing a service. It describes how to build the service (and what other services it depends on). Layers are composable — you can merge them, stack them, and provide them to Effects.

apps/chat/src/effect/index.ts
type AppRuntimeInput = {
  env: AppEnv;
  traceRecorder: TraceRecorderService;
  traceContext: TraceContextValue;
};

export const AppRuntime = {
  layer(input: AppRuntimeInput) {
    return Layer.mergeAll(
      Layer.succeed(AppEnvTag, input.env),           // Provides AppEnv
      Layer.succeed(TraceRecorder, input.traceRecorder), // Provides TraceRecorder
      Layer.succeed(TraceContext, input.traceContext),    // Provides TraceContext
    );
  },
};

Layer.succeed(tag, value) creates a layer that provides a pre-built value for a service tag. Layer.mergeAll combines multiple layers into one.

How Layers Are Used

// The bridge function — runs an Effect with all services provided
export function runAppEffect<A, E, R>(
  effect: Effect.Effect<A, E, R>,
  input: AppRuntimeInput,
) {
  return Effect.runPromise(
    effect.pipe(Effect.provide(AppRuntime.layer(input)))
    //    as Effect.Effect<A, E, never>  ← R is satisfied, so this compiles
  );
}

Effect Patterns — Effect.gen

Effect Pattern

Effect.gen is Effect's do-notation — a way to write sequential effect code that looks like async/await. Inside the generator, yield* "unwraps" an Effect to get its success value (or throws if it fails).

apps/chat/src/effect/index.ts — traceEffect
export function traceEffect<A, E, R>(
  name: string,
  kind: TraceSpanKind,
  attrs: Record<string, unknown>,
  effect: Effect.Effect<A, E, R>,
) {
  return Effect.gen(function* () {
    // yield* unwraps the Effect and gives us the value
    const recorder = yield* TraceRecorder;  // reads from Context
    const context = yield* TraceContext;    // reads from Context
    const spanId = createId("span");

    // Start a trace span (Effect.tryPromise wraps a Promise)
    yield* Effect.tryPromise(() =>
      recorder.startSpan({ spanId, traceRunId: context.traceRunId, ... })
    );

    // Create child context with updated parentSpanId
    const childContext = { ...context, parentSpanId: spanId } satisfies TraceContextValue;

    // Execute the inner effect with child context, and finish the span on exit
    return yield* effect.pipe(
      Effect.provideService(TraceContext, childContext),
      Effect.onExit((exit) => {
        const status = statusFromExit(exit);
        return Effect.tryPromise(() =>
          recorder.finishSpan({ spanId, status, ... })
        );
      }),
    );
  });
}

Reading the Generator Syntax

// Effect.gen(function* () { ... }) is syntactic sugar for Effect chains:
Effect.gen(function* () {
  const a = yield* effectA;    // run effectA, get its value
  const b = yield* effectB;    // run effectB, get its value
  return a + b;                // wrap in Effect.succeed
});

// Equivalent pipe form:
effectA.pipe(
  Effect.andThen((a) =>
    effectB.pipe(
      Effect.andThen((b) => Effect.succeed(a + b))
    )
  )
);
When to use gen vs pipe
Use Effect.gen when you have sequential steps that reference each other's results (like the trace function above). Use .pipe() when you have a linear chain of transformations that don't need intermediate values. In this codebase, gen is more common.

Effect Patterns — Effect.tryPromise

Effect

Effect.tryPromise wraps a Promise-returning function into an Effect. If the promise rejects, the Effect fails. This is the primary way we bridge async code into Effect. 

// Wrapping a Promise into an Effect
const effect = Effect.tryPromise(() =>
  recorder.startSpan({ spanId, traceId, ... })
);

// With a catch handler for custom error mapping
const effect = Effect.tryPromise({
  try: () => fetch("https://api.example.com"),
  catch: (error) => new NetworkError(String(error)),
});

Comparison: Effect.tryPromise vs raw try/catch

Traditional async/await with try/catch
async function doWork() {
  try {
    const result = await fetch(url);
    const data = await result.json();
    return data;
  } catch (error) {
    // Error is `unknown` — need to narrow
    if (error instanceof Error) {
      log.error("fetch_failed", { message: error.message });
    }
    throw error;  // re-throw, but caller must also try/catch
  }
}
Effect.tryPromise (error is part of the type)
const doWork = Effect.tryPromise(() =>
  fetch(url).then(r => r.json())
).pipe(
  Effect.catchAll((error) =>
    Effect.gen(function* () {
      yield* Effect.sync(() =>
        log.error("fetch_failed", { message: String(error) })
      );
      return yield* Effect.fail(error);  // typed failure
    })
  )
);
// The Effect type tells you exactly what errors can happen:
// Effect<Data, Error, never>

Effect Patterns — Effect.pipe

Effect

.pipe() is how you compose Effects in a readable, left-to-right chain. It's like Unix pipes — each step receives the output of the previous one. 

// Pipe chains read left-to-right
const program = Effect.tryPromise(() => fetch(url)).pipe(
  Effect.andThen((response) => Effect.tryPromise(() => response.json())),
  Effect.catchAll((error) => Effect.succeed({ fallback: true })),
  Effect.provide(AppRuntime.layer(input)),
);

In the codebase, .pipe() is used for:

  • Providing layers: effect.pipe(Effect.provide(layer))
  • Adding cleanup: effect.pipe(Effect.onExit(handler))
  • Error handling: effect.pipe(Effect.catchAll(handler))
  • Sequential chaining: effect.pipe(Effect.andThen(nextEffect))

How Tagged Errors Are Used

// In error normalization — pattern matching on _tag
function normalizeAssistantError(error: unknown): AppError {
  if (error instanceof CancelledError) return error;
  if (error instanceof RateLimitError) return error;

  // Check HTTP status codes from upstream providers
  if (isHttpError(error, 429)) return new RateLimitError("Rate limited by provider");
  if (isHttpError(error, 408)) return new ProviderTimeoutError("Provider timeout");
  if (isHttpError(error, 401)) return new AuthError("Invalid API key");

  return new UnknownUpstreamError(String(error));
}

// In trace recording — error type becomes the errorCode
function serializeError(error: unknown) {
  if (error instanceof Error) {
    return {
      errorCode: error._tag ?? error.name ?? "Error",  // _tag preferred
      errorMessage: error.message,
    };
  }
  return { errorCode: "UnknownUpstreamError", errorMessage: String(error) };
}

Comparison: Tagged Errors vs Error Codes

String error codes (common in REST APIs)
throw { code: "RATE_LIMITED", message: "Too many requests" };

// Problem: no type safety — you can throw any string.
// No instanceof check — must match on string.
catch (e) {
  if (e.code === "RATE_LIMITED") { ... }
  // What if someone typos "RATE_LIMTED"? No compile error.
}
Tagged error classes
throw new RateLimitError("Too many requests");

// Type-safe pattern matching

  if (e instanceof RateLimitError) { ... }
  // e._tag === "RateLimitError" — can also match on _tag
  // TypeScript narrows the type automatically
}

Effect Patterns — Effect.onExit

Effect

Effect.onExit is like finally, but for Effects. It runs a handler regardless of whether the effect succeeded, failed, or was interrupted. The handler receives an Exit value that tells you what happened. 

// From traceEffect — always finish the span, whether the inner effect
// succeeded, failed, or was cancelled
return yield* effect.pipe(
  Effect.provideService(TraceContext, childContext),
  Effect.onExit((exit) => {
    const status = statusFromExit(exit);  // "completed" | "failed" | "cancelled"
    const error = errorFromExit(exit);    // error details if failed
    return Effect.tryPromise(() =>
      recorder.finishSpan({ spanId, status, ...error })
    );
  }),
);

Comparison: Effect.onExit vs try/catch/finally

try/catch/finally
async function withSpan(name, fn) {
  const spanId = createId("span");
  await recorder.startSpan({ spanId, name });
  try {
    const result = await fn();
    await recorder.finishSpan({ spanId, status: "completed" });
    return result;
  } catch (error) {
    // Is it a real error or a cancellation?
    // Hard to tell with standard try/catch.
    await recorder.finishSpan({
      spanId,
      status: "failed",
      errorMessage: String(error),
    });
    throw error;
  } finally {
    // This runs, but we already finished the span above.
    // What if we need different cleanup for success vs failure?
    // We'd need to track state manually.
  }
}
Effect.onExit
// Single handler covers success, failure, AND interruption
const withSpan = (name, effect) =>
  Effect.gen(function* () {
    const spanId = createId("span");
    yield* Effect.tryPromise(() =>
      recorder.startSpan({ spanId, name })
    );
    return yield* effect.pipe(
      Effect.onExit((exit) => {
        // exit tells you exactly what happened
        const status = Exit.isSuccess(exit) ? "completed"
          : Cause.hasInterruptsOnly(exit.cause) ? "cancelled"
          : "failed";
        return Effect.tryPromise(() =>
          recorder.finishSpan({ spanId, status })
        );
      }),
    );
  });

Effect Anti-Patterns

These are patterns you should not use in this codebase.

Anti-Pattern 1: Using Effect.runSync for side effects

Anti-Pattern
// Don't do this — runSync throws on async effects
Effect.runSync(
  Effect.tryPromise(() => fetch(url))
); // 💥 Runtime error if the effect is actually async
Correct
// Use runPromise for async effects
await Effect.runPromise(
  Effect.tryPromise(() => fetch(url))
);

Anti-Pattern 2: Mixing async/await with Effect.gen

Anti-Pattern
// Don't mix async/await inside Effect.gen
const effect = Effect.gen(function* () {
  const data = await fetch(url);  // ❌ Don't use await inside gen
  yield* Effect.tryPromise(() => process(data));
});
Correct
// Wrap ALL async calls in Effect.tryPromise
const effect = Effect.gen(function* () {
  const data = yield* Effect.tryPromise(() => fetch(url));
  yield* Effect.tryPromise(() => process(data));
});

Anti-Pattern 3: Ignoring the error channel

Anti-Pattern
// Don't swallow errors — the type says it can't fail, but it can
const effect = Effect.tryPromise(() => riskyOperation()).pipe(
  Effect.catchAll(() => Effect.succeed(null)),  // ❌ Hides the error
);
Correct
// Handle errors explicitly and log them
const effect = Effect.tryPromise(() => riskyOperation()).pipe(
  Effect.catchAll((error) =>
    Effect.gen(function* () {
      yield* Effect.sync(() =>
        log.error("risky_operation_failed", { error: String(error) })
      );
      return yield* Effect.fail(error);  // Re-fail with context
    })
  ),
);

Anti-Pattern 4: Using Effect for everything

Anti-Pattern
// Don't wrap simple pure functions in Effect
const add = (a: number, b: number) =>
  Effect.gen(function* () {
    return yield* Effect.succeed(a + b);  // ❌ Unnecessary
  });

// Don't use Effect.runPromise for synchronous code
await Effect.runPromise(Effect.succeed(42));  // ❌ Adds overhead
Correct
// Pure functions stay as regular functions
const add = (a: number, b: number) => a + b;

// Use Effect.sync for synchronous side effects
const logMessage = Effect.sync(() => console.log("hello"));

// Use Effect only when you need:
// - Error handling (Effect.tryPromise)
// - Dependency injection (Context.Services)
// - Resource management (Effect.onExit)
// - Composition of effectful operations

Anti-Pattern 5: as any to silence type errors

Anti-Pattern
// Don't use `as any` to make things compile
const result = someEffect as any;  // ❌ Erases all type safety
const data = Schema.decodeUnknownSync(schema)(input) as any; // ❌
Correct
// Use proper type narrowing
const result = someEffect as Effect.Effect<MyType, MyError, MyContext>;

// Or use the typed decode helper
const data = Schema.decodeUnknownSync(schema)(input);
// data is already correctly typed — no cast needed
The as any Rule
The AGENTS.md explicitly forbids as any. It caused a real production bug (the "drive 400 incident") where a schema mismatch was hidden behind an any cast. If a type doesn't fit, use proper generics, unknown, type assertions to the correct type, or satisfies.

Authoring Conventions — Branded Types

The chat app uses branded types to prevent mixing up different kinds of IDs at compile time.

apps/chat/src/domain/index.ts
// A branded type adds a phantom brand to a primitive
type Brand<T, Name extends string> = T & { readonly __brand: Name };

export type WorkspaceId = Brand<string, "WorkspaceId">;
export type ThreadId = Brand<string, "ThreadId">;
export type MessageId = Brand<string, "MessageId">;

// Constructor function — validates and brands
function brandString<Name extends string>(value: string, brandName: Name): Brand<string, Name> {
  const trimmed = value.trim();
  if (!trimmed) throw new Error(`Invalid ${brandName}`);
  return trimmed as Brand<string, Name>;
}

export const toWorkspaceId = (value: string) => brandString(value, "WorkspaceId");
export const toThreadId = (value: string) => brandString(value, "ThreadId");
export const toMessageId = (value: string) => brandString(value, "MessageId");
// At compile time:
const wid: WorkspaceId = toWorkspaceId("wrk_abc123");
const tid: ThreadId = toThreadId("thd_xyz789");

function getThread(workspaceId: WorkspaceId) { ... }

getThread(wid);  // ✅ OK
getThread(tid);  // ❌ Compile error — ThreadId is not assignable to WorkspaceId
getThread("wrk_abc123" as string);  // ❌ Compile error — string is not branded
Why Branded Types?
Without branding, all IDs are just string. You could accidentally pass a thread ID where a workspace ID is expected, and TypeScript wouldn't catch it. Branding makes these mistakes compile-time errors.

export function createStructuredLogger(

  defaults: Record<string, unknown> = {},

  return {

Decision Log — Why We Do It This Way

Why Durable Objects for Chat (not D1)?

Decision: DO SQLite for Chat, D1 for Drive

Chat needs real-time state. A Durable Object is a single-instance, single-threaded actor. All WebSocket connections for a user land on the same DO, so there's no concurrency issues, no distributed locking, and event broadcasting is trivial (iterate over connected sockets).

Drive is request/response. No real-time sync needed. D1 (Cloudflare's managed SQLite) is simpler, cheaper, and doesn't require a DO class. The drive app can run as a plain ExportedHandler.

Alternative considered: Using D1 + Durable Objects for drive too. Rejected because drive doesn't need WebSocket sync, and DOs have higher operational cost (cold starts, alarms, storage limits).

Why a Custom Sync Protocol (not CRDT, not REST)?

Decision: Custom WebSocket sync with commands/events

CRDTs (like Yjs, Automerge) are designed for collaborative editing of shared documents. Chat doesn't have shared documents — each user has their own workspace. CRDTs would add complexity without benefit.

REST polling would work but gives poor real-time UX. The user would see delays between sending a message and seeing the streaming response.

The custom protocol gives us: optimistic updates (instant UI feedback), event sourcing (full audit trail), deduplication (safe retries), and efficient resume after disconnect (just replay events from last known seq).

Why Effect for Tracing (not OpenTelemetry SDK)?

Decision: Effect-based tracing with custom TraceRecorder

OpenTelemetry SDK is heavy and designed for server-side Node.js. It doesn't work well in Durable Objects (no long-running process, limited storage).

The custom approach uses Effect's Context.Services and onExit to create spans that are stored in the DO's SQLite database and synced to the client via events. This means traces are visible in the UI in real-time, not in a separate observability tool.

Why SolidJS (not React)?

Decision: SolidJS for both client apps

SolidJS provides fine-grained reactivity without a virtual DOM. Signals update only the DOM nodes that depend on them — no re-rendering entire component trees. For a chat app where streaming text updates the UI every ~50ms, this matters.

Also: SolidJS has no runtime overhead comparable to React (no fiber, no reconciler), which is important for a self-hosted deployment where bundle size affects cold start time.

Why No Effect on the Client?

Decision: Effect only on the server

Effect's runtime is ~50KB minified. For a self-hosted app, every kilobyte matters. The client doesn't need Effect's features (dependency injection, error channel, tracing) — it's a UI that receives events and dispatches commands. SolidJS's signals handle reactivity, and manual type-checking functions handle response validation.

Why Drizzle ORM (not Prisma, not raw SQL)?

Decision: Drizzle ORM with D1/DO SQLite

Prisma doesn't support Cloudflare D1 or Durable Object SQLite (it needs a long-running Node.js process for its query engine).

Raw SQL works but loses type safety — you'd need to manually type every query result.

Drizzle generates SQL at build time (no runtime query engine), has excellent TypeScript inference, and supports both D1 and DO SQLite drivers. The dual-schema pattern (Drizzle definitions + raw DDL) is a pragmatic compromise — Drizzle for typed queries, raw DDL for cold-start initialization.

Why HttpServerResponse.fromWeb() for File Downloads?

Decision: Hybrid Effect + raw Response for binary data

Effect's HttpApi is designed for JSON request/response. File downloads need streaming binary bodies with custom headers (content-disposition, content-type). HttpServerResponse.fromWeb() wraps a raw Web Response object so it can be returned from an Effect handler.

This is why the drive handlers use HttpServerResponse.fromWeb(new Response(object.body, { headers })) for downloads but return plain objects like { file: publicFile(row) } for JSON responses.
